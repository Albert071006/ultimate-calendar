# 计划 JSON 与上下文文件标准（v1 / v2）

外部 agent 可以直接生成 `*.calendar-plan.json` 文件。用户在 Windows 终极日历点击 **导入计划 → 选择 JSON 文件 → 核对预览 → 确认导入**，一次导入目标、任务、学习时段及资料关联。应用直接解析文件，不调用 AI，不需要逐个操作任务编辑器。

- [完整可导入示例](examples/study-plan.calendar-plan.json)
- [给已有任务补充四个时段的示例](examples/supplement-existing-tasks.calendar-plan.json)（须替换为真实任务 ID 与实际日期）
- [上下文示例](examples/study-plan.calendar-context.json) → [带状态校验的 v2 补录示例](examples/guarded-supplement.calendar-plan.json)（均为合成数据，正式使用应从应用重新导出）
- JSON Schema：[v1 新建计划](schemas/calendar-plan-v1.schema.json) · [v2 增量计划](schemas/calendar-plan-v2.schema.json) · [规划上下文](schemas/calendar-context-v1.schema.json)
- [规划规则与高级接口](agent-planning-guide.md)

这与“导入消息”“课表导入”“恢复备份”是不同入口。当前文件入口在 Windows 桌面；云模式写入现有共用资料服务，手机随后看到已保存的结果。文件生成成功时应报告“文件已生成，尚未导入”。

## 给外部 agent 的指令

> 首次建立计划时，请按本规范生成一份 UTF-8 的 `.calendar-plan.json` 文件。交付文件本身，不要只给 Markdown 或内部 mutate 请求。使用 `format:"ultimate-calendar-plan"`、`version:1`、`timezone:"Asia/Shanghai"`；为本次计划生成稳定唯一的 planId，每条目标、任务、时段也要有固定 id。用 goalRef、taskRef、resourceRefs 建立文件内关联，不要猜测日历数据库 ID。学习安排使用 kind:"work"，明确开始和结束时间；真实截止要求才写 deadline。网页资料放 resources，任务可继承目标资料。读取不到当前日历时请注明“未核对现有安排”，交给应用导入预览核对。输出只含数据，不包含 API Key、Cookie、确认令牌、脚本或数据库命令。失败重试必须使用原文件，不要更换 planId 再创建一遍。

> 如果我提供了 `.calendar-context.json`，请读取其中的 request、目标、任务、已有时段、资料和 busyIntervals，返回 `version:2` 的增量计划，并将整个 basis 原样复制到计划顶层。goals 保持空数组；原任务补时段只新增 blocks，用 taskId 引用原任务；同一目标下确需新增任务时，用 goalId 引用 basis.goalId。时段必须关联原任务或本文件新任务，全部位于导出的规划日期范围内，不能为已完成任务追加时段。每个新的补录或下周安排批次使用新的 planId，同批失败重试保留原文件。不要把上下文原样当作导入文件，不要修改 basis、重新创建已有事项，或用新增替代移动／删除。

## 已有计划的增量补录与续排

推荐流程是：**取得当前计划上下文 → 外部 agent 生成增量安排 → 在日历预览并导入**。首次建立计划和在原计划上追加安排都使用 `.calendar-plan.json`，区别在于是否需要新建目标、任务。

### 当前能力与文件用途

| 文件／入口 | 用途 | 当前状态 |
| --- | --- | --- |
| `.calendar-plan.json`，v1 | 只包含本批需要新增的目标、任务或时段 | 保持兼容；可关联已有记录，但不校验导出时的状态 |
| `.calendar-plan.json`，v2 | 根据一个目标的上下文追加任务／时段 | 已支持；必须原样携带 `basis`，导入时核对来源及状态变化 |
| `.calendar-context.json` | 保存当前目标、任务、安排和规划约束，交给 agent 阅读 | 在“我的 → 目标”的目标行或目标详情点击“导出给外部智能体”；上下文不能直接导入 |
| 日历备份 | 保存、恢复完整资料 | 不是计划上下文文件，也不能作为增量计划导入 |

日常使用：在 Windows 选择目标并点击“导出给外部智能体”，选择规划起止日期（含首尾，最多 366 天），填写续排要求（可选），点击“预览导出内容”，核对数量后“保存上下文文件”。默认隐藏其他日程名称；目标关联任务及其时段会全部导出，日期范围限制的是忙碌信息。预览有效期为 10 分钟，保存前会重读并核对资料变化。操作只保存本地文件，不调用 AI，不自动发送给任何外部服务。

也可由具有已授权、已配对读取能力的客户端取得相关资料。若使用用户指定的备份提取编号，只在本地抽取目标相关内容，不需要恢复备份。真实 ID 尚未取得时，不能凭同名匹配、猜测 ID 或再建一套任务绕过。推荐通过实际导出取得可校验的 `basis`。

### 上下文文件应提供什么

导出文件名默认为 `目标名称.calendar-context.json`，格式为 `format:"ultimate-calendar-context"`、`version:1`、`timezone:"Asia/Shanghai"`。用户续排要求位于 `request`，文件自带 `instructions` 说明如何生成增量计划。以下内容供 agent 阅读；导入计划只携带 `basis`，不能夹带完整上下文：

| 内容 | 要求 |
| --- | --- |
| `basis` 来源与状态 | `source`（`kind`、`dataInstanceId`，云端还有 `generation`）、`goalId`、`fromDate`、`toDate`、`exportedAt`、`fingerprint`。无路径、地址或会话凭据；必须完整原样复制到 v2 计划 |
| 所选目标 | 真实 `id`、`version`、名称、说明、状态、目标日期 |
| 关联任务 | 真实 `id`、`version`、目标／课程关联、名称、说明、`status`、真实 DDL 和提醒配置；同时保留已完成、未完成任务，供 agent 判断续做范围 |
| 已有时段 | 与这些任务关联的时段，含真实 `id`、`version`、`taskId`、名称、开始与结束、类型、完成／取消状态；已有重复系列保留其关联标识 |
| 资料引用 | 目标、任务、时段的直接资料及继承来源；仅保留已有引用，不导出附件正文或电脑绝对路径 |
| 忙碌区间 | 规划日期范围内，按教学周和调课／停课展开的课程，以及其他已确认活动的具体起止时间；无关事项可隐藏名称。说明覆盖范围，不能把读取失败表示成“没有安排” |
| 规划约束 | 用户明确给出的可用时段、每天投入上限、休息要求和本次续排要求；没有给出的内容标明未知或假设 |

完成状态与任务说明按实际资料导出。当前没有独立的预计耗时、学习用时或百分比进度字段，不应把修改时间解释成完成时间，也不能凭空补出学习记录。目标相关时段用于判断已有安排，忙碌区间用于避让其他事项，两者的同一时段不能重复计入占时。

### agent 如何生成增量文件

1. **原任务只缺学习时段：** 使用 `version:2` 并原样复制 `basis`，`goals:[]`、`tasks:[]`，只在 `blocks` 添加缺少的时段，每条使用真实 `taskId`。保留原有时段，不在新文件里重复输出。
2. **同一目标下安排下周的新任务：** `goals:[]`，新增任务使用真实 `goalId`；新时段用 `taskRef` 关联本文件新任务。还没做完的旧任务继续使用原 `taskId` 安排，不重新创建任务。
3. **资料复用：** 原任务已关联目标／课程的公共资料会继承显示，无需复制到每个新时段。仅为本次新增的直接资料填写 `resources` 和 `resourceRefs`。
4. **批次编号：** 一次独立的补录或下周安排使用新的 `planId`；标题可以标明“补录”或日期范围。同一批失败重试必须保留原文件、`planId` 和条目 `id`。不能把已导入的完整计划换个编号再导入。
5. **保留旧安排：** 改时间、缩短、替换、取消或删除已有时段都属于修改，v1 和 v2 均不支持。使用应用编辑器或已有获授权更新接口；不能以“新建相同时段”冒充移动。

v2 专用于所选目标的增量续排：`goals` 必须为空；新任务必须用 `goalId` 指向 `basis.goalId`；新时段必须引用所选目标内未完成的原任务，或用 `taskRef` 引用本文件的新任务。不能引用无关目标／任务／课程，不能新增无任务归属的时段。所有新增时段须完全位于 `fromDate` 零点至 `toDate` 次日零点之间，结束恰为次日零点允许。想安排范围外的日期，应重新导出覆盖该日期的上下文；不要修改原 `basis`。

参见 [上下文示例](examples/study-plan.calendar-context.json) 和 [v2 四个时段的增量示例](examples/guarded-supplement.calendar-plan.json)。它们使用虚构数据；正式规划应以应用实际导出的上下文为准，原样复制其 `basis`，再引用其中真实任务 ID 并安排实际日期。示例没有重复包含四个任务本身，导入器也不会为不存在的 `taskId` 自动建任务。旧版 [v1 补录示例](examples/supplement-existing-tasks.calendar-plan.json) 仅用于兼容说明。

### 重新核对与验收

上下文只是导出时的快照。生成增量文件前，应尽可能重读相关任务是否完成、关联是否改变、原时段是否移动以及课表是否更新；无法重读时说明核对时间和缺失内容，由用户在导入前核对。

**v2 导入器**会核对 `basis` 的资料来源、所选目标及其关联任务／时段／资料、指定范围的忙碌信息。任务完成、旧时段移动／取消、相关资料或课表占用变化等会使状态校验失效，未完成条目会被阻止，提示重新导出并生成补充方案；缺失引用、引用已完成任务或超出范围同样不能继续。它不会自动改回旧状态，也不会自动移动课程来消除冲突。

中断续导时，本批已经保存的内容会按原回执核对，并从导出基线比较中排除，避免把自身新增误判成外部变化。若期间还有其他变化，先核对原请求的结果，保留已保存部分，再重新导出；新的补充文件只包含仍缺少的内容。同一文件已全部导入时不会重复创建。

如果上次保存成功但响应丢失，之后原计划又发生变化，应用在能从同一资料的操作日志确认原操作已成功时提供“仅核对已保存操作”。此按钮只核对原请求并补齐回执，不会继续新增，也不能勾选允许冲突。核对后重新导出当前上下文，再生成仍缺少的安排；资料来源变化或成功证据缺失时继续保留待核对保护。

**v1 保持原有语义**：只检查现有引用、冲突及预览之后的变化，没有导出基线校验。不要给 v1 加 `basis` 或 `expectedVersion`，也不要把被 v2 阻止的文件改成 v1 来绕过检查。自动更新／删除旧安排仍是后续能力，需要独立协议和修改前后预览。

验收示例（虚构数量）：原资料有 **1 个目标、6 个任务、2 个时段**，只补剩余 4 个时段后，应仍有 **1 个目标、6 个任务，时段增加到 6 个**；原两段不变，新增四段关联正确。重复导入同一补录文件数量不再增加；中断后使用原文件核对并续导，不重建已保存部分。

## 最小任务文件

```json
{
  "format": "ultimate-calendar-plan",
  "version": 1,
  "timezone": "Asia/Shanghai",
  "planId": "reading-2026-11-02-unique-01",
  "title": "阅读计划",
  "tasks": [
    {
      "id": "read-01",
      "title": "阅读第一章并整理三条笔记",
      "description": "完成标准：能用自己的话解释三个概念。"
    }
  ]
}
```

文件可以只包含任务。未安排时段的任务会进入待安排；不能把截止时间当作执行时间。

## 顶层字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `format` | 是 | 固定 `ultimate-calendar-plan` |
| `version` | 是 | `1` 为通用新增；`2` 为按目标上下文增量续排，不是计划修订号 |
| `basis` | v2 必填 | 从应用导出的上下文原样复制；v1 不接受 |
| `timezone` | 是 | 固定 `Asia/Shanghai` |
| `planId` | 是 | 本次计划的唯一固定编号，1–80 位字母、数字、点、下划线、短横线，首位为字母或数字 |
| `title` | 是 | 计划名称，1–500 字符 |
| `goals` | 否 | 目标数组，默认 `[]` |
| `tasks` | 否 | 任务数组，默认 `[]` |
| `blocks` | 否 | 执行时段或活动数组，默认 `[]` |
| `resources` | 否 | 资料引用数组，默认 `[]` |

导入文件采用 UTF-8 JSON（可有 BOM），最多 1 MiB。目标、任务、时段合计 1–500 条；资料最多 500 条。上下文导出最多 16 MiB，不能直接导入。每组内 `id` 必须唯一，条目编号格式与 `planId` 相同。文件中的编号只是文件内关联键，由应用映射到真实记录 ID。未知字段会被拒绝；不要写入 `$schema`、`revision`、`operationId`、`confirmed`、`expectedVersion` 或任意执行指令。需要 JSON Schema 校验时在编辑器配置对应版本的 Schema 文件。

## 目标 `goals[]`

必填 `id`、`title`。可选字段如下：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `description` | `""` | 完成标准、说明，最多 100,000 字符 |
| `priority` | `"medium"` | `low` / `medium` / `high` |
| `targetDate` | `null` | `YYYY-MM-DD`，目标日期 |
| `status` | `"active"` | `active` / `completed` / `paused` |
| `color` | `null` | 建议省略，由应用分配；可选值见 Schema |
| `resourceRefs` | `[]` | 引用顶层资料的 `id`，最多 50 项 |

## 任务 `tasks[]`

必填 `id`、`title`。可选 `description`、`status`（`open` / `done`，默认 `open`）、`deadline`、`goalRef`、`goalId`、`courseId`、`reminders`、`resourceRefs`。

- `goalRef:"goal-01"` 关联本文件 `goals` 中的目标，应用自动取得真实 ID。
- `goalId` 仅用于关联**已读取并核实**的现有目标 ID；不能与 `goalRef` 同时填写。
- `courseId` 仅用于关联已读取并核实的现有课程 ID，默认 `null`。
- `deadline` 默认 `null`；有真实 DDL 时写 `{"date":"2026-11-04","time":"21:00"}`。仅知道日期时写 `time:null`，不要擅自补 23:59。
- 首次新建计划可用文件内关联；给已有计划补录时必须核实对应真实 ID，不能留空后另建独立事项，也不能用课程名称冒充 ID。

## 时段 `blocks[]`

必填 `id`、`title`、`start`、`end`。可选 `kind`、`taskRef`、`taskId`、`location`、`reminders`、`resourceRefs`。

```json
{
  "id": "reading-session",
  "taskRef": "read-01",
  "title": "第一章阅读与笔记",
  "kind": "work",
  "start": "2026-11-02T19:10:00+08:00",
  "end": "2026-11-02T19:55:00+08:00"
}
```

- `kind` 默认 `work`（学习／执行）；固定活动使用 `event`。文件标准中两者都必须有明确 `end`，且结束晚于开始。
- 时间必须是有效的上海时间 ISO 字符串，带秒和 `+08:00`；不接受 `Z`、缺时区的时间、`24:00` 或不存在的日期。可含三位毫秒。
- `taskRef` 关联本文件任务；`taskId` 关联已核实的现有任务，两者互斥。v1 都不填时创建独立时段；v2 必须关联所选目标的任务。
- 一个任务可以有多个时段，分别使用不同 `id`。不要为每次学习重新创建同一任务。
- v1、v2 均不接受 RRULE 或循环表达式；有限重复安排请展开成各自的时段。它们是独立时段，没有重复系列的批量修改语义。
- `location` 默认 `""`，最多 2,000 字符；不要包含电脑文件路径。

## 资料与提醒

网页资料放在顶层 `resources`：

```json
{
  "id": "course-notes",
  "kind": "web",
  "name": "课程讲义",
  "url": "https://example.com/course"
}
```

在目标、任务或时段中写 `"resourceRefs":["course-notes"]`。网页仅支持 `http` / `https`，不接受账号密码、脚本或 `file://`。关联不会抓取网页，也不会把正文发给 AI。

电脑文件／文件夹须先通过应用的“关联资料”登记，再把返回的完整 `{id,name,kind,deviceId,deviceName}` 放入 `resources`，用返回的 `id` 引用。导入会核实引用属于本机已登记资料。v1、v2 均不接受原始 `path`，也不会扫描、上传或自动打开电脑文件。文件移动后在原电脑重新定位。公共资料挂在目标上即可，关联任务及其时段会继承显示。

任务和时段的 `reminders` 默认继承全局设置。明确要求准时提醒时可写：

```json
{"enabled":true,"leadMinutes":[0],"dateOnlyTime":null}
```

`leadMinutes:null` 继承全局；`[15]` 提前 15 分钟；`[]` 不产生提醒。任务 DDL 提醒和时段开始提醒相互独立，不要重复制造同一提醒。

## 预览、保存与失败续导

1. 选择文件时只校验和读取当前资料，不创建任务，不调用 AI。核对目标／任务关联、资料引用、字段、截止日期和时间。
2. 预览列出新增、已有、需要处理的条目；时间冲突单独列出。应用按当前课程教学周、调课／停课、已有活动与文件内时段检查重叠。边界相接不算重叠；DDL 不占用时间。
3. 默认遇到时间冲突需要核对后勾选继续；未勾选不会导入冲突计划。已删除、已修改的导入记录、缺失引用等阻止续导，不会覆盖或重新创建。
4. 确认后按目标 → 任务 → 时段保存并自动处理关联。整个文件由多个事务组成；中断会保留已成功部分，并显示剩余内容。不是失败后自动回滚整个计划。
5. 同一文件再次导入使用原计划和条目编号，已确认保存的部分不会重复创建。失败后保留原文件，在同一资料连接重新选择它，核对后继续剩余项；不要换 `planId` 重试。
6. 导入后文件保持不变。修改同一 `planId` 的内容会被拒绝；需要调整已安排内容时直接编辑现有任务／时段。确实新增的计划、同一目标下的补录或下周安排均可作为新批次使用新的 `planId`，并只包含需要新建的条目，通过真实 ID 沿用原目标／任务。
7. 去重依据计划编号、条目编号和导入回执，不会仅凭同名合并手工创建的任务。需要关联现有目标或任务时使用真实 `goalId` / `taskId`。
8. 预览之后资料发生变化、云端身份／资料代际改变或操作结果尚未确定时会暂停。重新核对提示与原文件；不能把旧计划自动写到另一份资料。

导入进度保存在当前应用的私有资料目录；不要清理它来“修复”重复导入。不要改写本机旧数据库来替代云端导入。云模式需要连接当前共用服务；断网不会冒称已导入。普通文件导入无需 API Key、软件发布或重新安装。

JSON Schema 用于静态字段校验；引用是否存在、编号唯一、真实日期、时间先后和当前课表冲突仍由应用最终检查。
